# 実装とテストの進め方

正本は[テスト設計](../../../docs/design.md#test-design)。実行方法は[開発・検証ガイド](../../../docs/development.md#development-workflow)と[package.json](../../../package.json)。成立条件を変える場合は[要件](../../../docs/ui-requirements.md)・[技術判断](../../../docs/operations/README.md)も読む。

## 実装前に進め方を選ぶ

Issueの目的・受入条件と、変更が失敗した場合の影響を先に確認する。**振る舞いを変更するときはテストファーストを原則**とし、変更の性質・リスク・仕様の明確さ・自動テストの有効性に応じて選ぶ。

| 変更 | 進め方 |
| --- | --- |
| 新機能・ロジック／契約の変更 | 期待する振る舞いのテストを先に用意し、意図した失敗を確認して最小限を実装する |
| バグ修正 | 再現操作列を回帰テストにし、修正前の失敗を確認してから修正する |
| 振る舞いを変えないリファクタリング | 既存テストで保護し、不足する重要なケースだけ補ってから変更する |
| UIの見た目・文言のみ | まず変更し、表示と影響箇所を確認する。動作や契約を変えるならテストを先行する |
| 成立性の調査・使い捨て試作 | まず検証し、採用する仕様が固まったら製品実装に必要なテストを設計する |
| 文書・CI設定のみ | 変更内容に合ったリンク・設定・ツール検証を選び、不要な製品テストは増やさない |

テストが先に書けないときは理由を明確にする。仕様が不明なら実装で推測せず確認し、実入力やOS依存の動作は自動テストだけで確証したことにしない。

## 不具合・実入力失敗の切り分け

原因が明白でない失敗では、推測で判定条件を変える前に次を行う。軽微で原因が明白な修正に形式的な調査書は不要。

1. **症状と証拠を固定する。** 期待値・実際の結果・再現操作列・対象revision/build・試験環境を最小限記録する。人工fixture、自然入力、本人申告を区別し、未観測の部分は仮説とする。
2. **失敗した境界を絞る。** 入力受信→中立状態→候補生成→棄却/取消→確定→通信→保存/通知/UIのうち、どこまで観測できたかを確認する。全工程の生ログを集めるより、初めて期待と食い違った箇所を探す。
3. **仮説を区別する検証を先に選ぶ。** あり得る原因を少数挙げ、それぞれを判別できる最小のテスト・計測を選ぶ。OS固有のUI・HWND・イベント順序など、未確認の挙動を成功必須条件として実装しない。観測でしか判別できないときは隔離probeを使い、実入力には本人の明示同意を得る。
4. **証拠に対応する最小修正を行う。** 可能なら失敗操作列のRedを本番policy/契約に沿う回帰試験にしてから修正する。正常系と、修正によって誤計上・誤通知し得る負例を合わせて確認する。仕様の期待値を修正案に合わせて弱めない。
5. **同じ失敗の無根拠な反復を止める。** 修正や再試行後も同じ症状で原因を区別できなければ、次のパッチの前に観測箇所・前提・別仮説を見直す。2回続けて新しい証拠が得られなければ、診断方法を切り替えるか未解決として報告し、同じ試行を繰り返さない。

診断には、必要な場合のみ**理由別の有界な集計や固定カテゴリ**を使う。診断の追加・削除で本番の判定が変わらないよう、判定と計測を分離し、診断設定や理由の取りこぼしも検査する。生キー・窓情報・入力時刻列などの禁止データを記録しない。通常の製品経路に診断を保存・外部送信せず、隔離検証の条件を守る。

## テスト設計と実装

1. **期待値を仕様から決める。** 入力→観測できる結果（記録・通知・保存・停止状態など）で検証し、内部実装・private呼出しに依存しない。UI/API変更では契約→unit/IPC mock→smokeのselector・待機・表示期待→配布試験の対応を確認する。旧fixtureや検出器の出力を正解にしない。
2. **必要なケースに絞る。** 正常・負例・境界・故障から、壊れた場合の影響と既存テストの不足に応じて選ぶ。既存テストで保護できるなら新規テストは不要。件数やcoverageだけを目的に追加しない。
3. **テスト先行なら意図した失敗を確認する。** 新機能は未実装の振る舞い、バグは再現操作列によるassert失敗を確かめる（構文・準備エラーをRedとしない）。関連ケースをまとめて先に書いてよく、1テストごとのRed→Greenは強制しない。既存の正しい挙動への追加試験は最初から成功してよい。
4. **最小限を実装して段階的に検証する。** テストを通すために期待値を弱めず、未要求の分岐・抽象化・機能を増やさない。まず関連テスト、次に影響した層、PRでは必要なCIを確認する。修正中の絞り込み結果を全件合格と扱わない。
5. **本番の経路と隔離範囲を守る。** Core、Mainの通信・保存・通知、本番C# policy、実helper、Electron UI、配布物は別の証拠。OS・Electron・ファイルI/Oは境界でfakeにし、内部の判定器やキューには本番コードを使う。非同期順序はdeferred、期限は仮想時計を使い、fakeは各試験で片付ける。
6. **既存配置に従う。** 新しいNode試験は`tests/*.test.ts`へ置く。helper/SDKが必要なら`native`で始め、本番C# policyは`tests/native-policy`へ追加してC#→TS契約を保つ。保存・移行は[故障境界](../../../docs/design.md#storage-review)の該当ケースを実装前の選定・PR前のレビューで確認する。

## 検証・レビューの反復を抑える

- 調査・修正中は、直前の仮説を判別する最小テストから実行する。原因の異なる失敗を分け、成功済みの検証はrevision・build・環境に結び付けて再利用する。
- 関連する修正と回帰ケースがまとまってから、影響層のsuite・同梱版作成・実機確認へ進む。変更のない生成物で繰り返しpackageしない。実機操作の前にpanel・対象窓・試験手順・制限時間を確認し、本人の操作ミスを製品の失敗と混同しない。
- レビューは[GitHub操作Skill](../github-workflow/SKILL.md)に従い、PR前の安定した変更全体と、重要なロジック変更後の必要な差分を対象にする。一時診断の試行や細かな編集ごとに全体レビューを追加しない。必須レビュー・CI・自然入力受入を削減対象にしない。
- 長期化した場合は、確定した原因・棄却した仮説・残る課題・証拠場所・最後に検証したrevision・次の検証を短く残す。会話履歴やテストの生ログを繰り返し読み込まず、工程の区切りで圧縮・引継ぎを検討する。

## 変更範囲に応じたテスト選択

修正中は差分・呼び出し元・利用先から必要な層だけ選び、実行ファイルと結果を記録する。絞り込みの成功を全件合格と扱わない。

| 変更箇所 | まず確認するテスト | 影響がある場合に追加 |
| --- | --- | --- |
| Markdownのみ | 文書リンクと内容の整合 | 実装変更があれば関連層のテスト |
| Core/Shared | 関連unit、型検査 | C#→TS候補契約ならnative policyとhelper結合 |
| Main/IPC・保存・通知 | 関連unit、該当する故障操作列 | Electron smoke、保存・終了契約なら同梱smoke |
| Renderer/Preload | UI・IPC unit、型検査 | Main結合smoke、同梱契約ならpackaged smoke |
| native-helper/C# | 本番C# policy、helper build・native suite | TSとの契約試験、関連Core・Electron smoke |
| scripts/CI/package | 対応するtool試験と設定検証 | build・package・配布smoke |

対象unitは`npm.cmd run test:unit -- --file=対象.test.ts`、nativeはhelperをbuild後に`node scripts/test/test.mjs native --file=native-policy.test.ts`などで絞る。詳細はREADMEを正本とする。

PRでは実装・テスト・設定・workflowを変更したらWindowsフルCIを維持する。MarkdownのみはフルCIを省略するが、必須チェック`windows-quality`は成功させる。依存関係が不明なら安全側に検証を広げる。

自動試験は隔離fixtureだけを使う。実入力観測は本人の明示的な同意後に行い、人工入力を認識率の証拠にしない。通常userData・他アプリ画像・入力内容を試験artifactに含めない。コミット・push・公開の許可はこのSkillから与えない。

完了時は、確認した本番経路、実行結果、修正した不具合、残る実機・配布確認を簡潔に報告する。coverageは計測対象を添え、skipや未実行を合格へ置き換えない。
