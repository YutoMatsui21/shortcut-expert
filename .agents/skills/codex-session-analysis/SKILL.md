# Codexセッション分析

## 基本方針

分析の正本はローカルのRollout JSONL。対象ログは読み取り専用とし、全文をモデルへ渡さない。**品質に必要な証拠を残しながら、モデルとツールの往復・ツール出力・再調査の総量を減らす。** 出力文字数やツール回数の一方だけを最小化しない。

調査は「対象特定 → `report` → 必要な根拠の確認 → 原因と改善策の判断」の順に進める。最初からすべての呼び出しを精査せず、重要な仮説・疑問を絞る。新しい証拠が必要なら調査範囲を広げてよい。レビュー・テスト・CIなど、品質維持に必要な工程を機械的な削減対象にしない。

## 分析手順

1. **対象セッションを確定する。**
   - 依頼・会話・既知の記録に確定済みのJSONLパスがあれば再検索しない。直近の実行が対象でパスが不明なら次の少数件を確認する。
     `python -B .agents/skills/codex-session-analysis/scripts/analyze_session.py overview --last 3 --project .`
   - 過去のPRなど直近以外が対象なら、関連する日付のフォルダーを絞ってファイル名だけを検索する。PowerShellではBashの波括弧展開を使わない。
     `rg -l -F 'pull/116' "$HOME/.codex/sessions/2026/10/28" -g 'rollout-*.jsonl'`
   - 過去の分析履歴も一致するため、候補の開始時刻とPR作成操作の記録を照合する。行番号が必要なら候補ファイルだけで`rg -n -o -m 2 -F 'gh pr create' "<候補JSONL>"`のように一致部分を取得する。JSONLの長い1行を`rg -n`で丸ごと出力しない。
   - `MEMORY.md`などの広範囲検索やGitHub参照は、対象の特定に足りない情報がある場合だけ行う。PR情報の照合が必要ならGitHub操作Skillに従い、例：`gh pr view 116 -R YutoMatsui21/shortcut-expert --json createdAt,url`。同じ確認を繰り返さない。

2. **1回の`report`から分析の重点を決める。**
   `python -B .agents/skills/codex-session-analysis/scripts/analyze_session.py report --file "<JSONLのパス>" --top 5 --max-total-chars 6000`
   トークンの内訳・応答ごとの入力規模・ターン別集計・先頭8件と出力量の多い区間・長時間処理・失敗・重複・切り詰め候補を確認する。候補の`summary`とIDを使って、原因の判断に必要な疑問を絞る。`truncated`と`omitted`を確認し、省略された候補を問題なしとみなさない。`report`で十分な数値を`overview`や`calls`から再取得しない。

3. **必要な証拠だけを適切な方法で取得する。**
   - ツールの引数・結果・前後の経緯：`detail --file "<JSONLのパス>" --id 7 --around 0 --max-chars 1200 --max-total-chars 2500`
   - レビュー指摘・承認など、行番号が分かるメッセージ本文：`message --file "<JSONLのパス>" --line 255 --max-chars 1500`
   - 呼び出し順・操作概要：`calls --file "<JSONLのパス>" --ids 1,23,34`。連続範囲が必要なら`--from-id 24 --to-id 32`。全件一覧は目的がある場合に限る。
   - 上記はすべて`python -B .agents/skills/codex-session-analysis/scripts/analyze_session.py`のサブコマンド。対応する機能があるのに独自PythonでJSONLを再解析しない。追加取得では必要なID・行番号・範囲を指定する。

4. **往復回数と出力量を両立させる。**
   - 独立した根拠が複数必要と分かっている場合は、**2〜3件程度を1回の外側のツール呼び出しにまとめてもよい**。例えば`detail`の各`--max-total-chars`を2,000〜3,000文字とし、合計6,000〜8,000文字程度を目安にする。並列実行は`AGENTS.md`の最大2件を守り、3件目は逐次実行する。固定の上限ではなく、必要な証拠の量に合わせる。
   - 先の結果で次の調査対象が変わる場合は、まとめて取得せず結果を見てから進む。単にツール回数を減らすために無関係な情報を一括取得しない。逆に、出力を小分けにするためだけに独立した取得を1件ずつ呼ばない。
   - 取得結果が切り詰められた場合は、判断に必要な欠落箇所だけ上限や周辺範囲を広げる。同じID・数値を理由なく再取得しない。

5. **十分な根拠が揃ったら終了する。** 重要なボトルネックごとに、①実測値・行番号・ツールID、②何が必要で何に改善余地があるか、③品質を維持した改善案、が説明できれば追加調査を止める。未解明で結論に影響する点だけ調べ、確定できなければ未確認として報告する。細部の網羅や呼び出し回数の達成を目的にしない。

## 判断と報告の注意

- トークン数は非キャッシュ入力・キャッシュ済み入力・出力・合計を区別する。履歴の再入力を含む合計トークンだけから、費用や改善効果を断定しない。ツール出力文字数はトークン数ではない。待機時間とトークン消費も別に扱う。
- `report`の応答別・ターン別記録が不明なときは推測で補完しない。`output_timeline`の8件区間は呼び出し順であり、開発工程の意味的な分類ではない。
- 失敗・待機・重複・切り詰めは調査候補であって無駄の確定ではない。`exit_code`が不明または0でも、内部コマンドの`ParserError`・例外・認証エラーが隠れる場合がある。観測した失敗は根拠とともに扱い、未検出を成功と断定しない。
- レビューによる回帰検出、最新headのCI、承認待ちなどは必要性を個別に評価する。親セッションと別のレビュー・サブエージェントの記録を混算せず、対象範囲を明示する。
- 同じ条件の実行でも応答・キャッシュ率・調査範囲が変わる。トークンや時間の変化をSkillだけの因果効果と断定せず、分析品質も比較する。

## 制約と検証

調査のみの依頼ではログ・ソース・設定・Skillを変更しない。認証情報や生ログを公開リポジトリへコピーしない。内部待機の実測が必要なら、利用可能なOTelデータを別途調べる。

スクリプトを変更した場合は`python -B -m unittest discover -s .agents/skills/codex-session-analysis/scripts -p "test_*.py"`を実行し、実際のJSONLでも集計値・出力上限・根拠IDを確認する。
