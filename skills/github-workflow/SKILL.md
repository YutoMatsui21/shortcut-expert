# GitHub操作

GitHub操作はこのSkillに従う。[AGENTS.md](../../AGENTS.md)と対象Issueの受入条件を優先する。コマンドや監視方法の詳細は[開発手順](../../README.md#development-workflow)・[PR監視入口](../../docs/development-tools.md#pr監視)を参照する。

## 1. GitHubの操作方法

1. **GitHub CLI（`gh`）を最優先**で使用する。
2. `gh`が使えない場合に限り、接続済みの`codex.apps`（GitHubアプリ）を使用する。
3. どちらも使えない場合は処理を停止し、ユーザーに報告する。

**判定・制約**
- CLIの利用可否は`gh --version`・`gh auth status`で確認する。
- 情報取得では`--json`・`--jq`を使い、必要な項目だけを取得する。
- 検索結果0件やコマンド失敗だけでCLIが利用不能とは判断しない。原因を確認する。
- 認証・権限は実行環境ごとに確認する。

## 2. 実装Issueの完了フロー

### 2.1. 実装・ローカル検証

1. 対象Issueの目的・受入条件、関連する要件・設計を確認する。
2. 必要な実装・修正を行う。
3. [テスト設計Skill](../test-shortcut-coach/SKILL.md)に従い、変更に対応する試験を実行する。

**制約**
- 人工fixtureの成功を実入力精度の証拠にしない。
- 変更範囲・検証結果・未検証事項を区別する。

### 2.2. PR前にローカルレビュー

1. [追加レビュー規則](../../docs/code-review.md)に従い、Issue・仕様・受入条件と変更内容を照合する。
2. 原則としてCodexの専用レビュアーにPRへ出す変更全体を確認させる。対話操作では`/review`、実装Agentがシェルから起動する場合は非対話の`codex review --base main`（未コミットの差分は`codex review --uncommitted`）を使う。必要に応じてコミット前後の対象を分け、意図したファイルを漏らさない。
3. 専用レビュアーが追加規則ファイルを参照したことは自動的に保証されない。適用を確認できない場合は`/review`のCustom instructions、または`codex review 'レビュー対象はmainとの差分。docs/code-review.mdの4観点を確認すること'`のようなカスタム指示を使う。`codex review`の`--base`・`--commit`・`--uncommitted`とPROMPTは同時指定できないので、カスタム指示使用時はレビュー対象も明示して実際の対象を確認する。
4. 指摘を関連コード・仕様と照合し、P0/P1は必ず対応、P2は重要度・緊急度を評価して必要なものに対応する。修正内容に応じて再テストし、重要なロジック変更があれば必要な範囲を再レビューする。
5. PR作成直前に、最後の全体レビュー対象となったコードの状態（コミットまたは作業差分）を記録する。レビューを省略した場合は理由を明記する。

**制約**
- レビューは修正・テストの代替ではない。専用レビュアーが利用できない場合は実施済み扱いにせず、阻害要因を報告する。
- 文書・CI設定だけの変更など、本番動作に影響しない差分は理由を記録してローカルレビューを省略してよい。

### 2.3. PRを作成する

1. 変更をcommit・pushする。
2. main向けPRがなければ作成する。
3. PR本文に対象Issue（例：`Closes #17`）、変更点・テスト結果・未確認事項を書く。
4. GitHubの`@codex review`は原則依頼しない。自動レビュー設定が有効になっていないか確認し、意図しない二重レビューを避ける。

**GitHubレビューを追加する条件**
- 保存データの破損・消失、マイグレーション、不可逆な削除、権限・プライバシーなど、影響が大きく復旧が難しい変更。
- ユーザーが明示的に求めた場合。
- 実装Agentが追加検証を必要と判断した場合は理由を示して依頼する。

必要な場合のみ`gh pr comment <PR番号> --body '@codex review'`を投稿する。同じheadへの重複依頼は避ける。

### 2.4. 最新headのCIを待つ

1. 最新headの完全SHAを取得する。
2. `gh pr checks <PR番号> --watch --interval 30`でCIの完了を待つ。
3. 実行中は待機し、ツールが利用できる範囲で定期的に状態を確認する。長時間未完了なら原因・状態を報告する。

**判定・制約**
- 対象：最新headの必須チェック`windows-quality`。未開始・skip・古いheadの成功を合格扱いにしない。
- 生ログを全量Codexに返さず、まず成否と失敗箇所を絞る。実行エラーとCI失敗を区別する。
- GitHubレビューを依頼していない場合、レビュー結果が存在しないことはCIの失敗でもMerge阻害条件でもない。

### 2.5. GitHubレビューを依頼した場合だけ結果を待つ

1. [PR監視入口](../../docs/development-tools.md#pr監視)で最新headの状態を確認する。

   `node scripts/github-workflow.mjs pr-status <PR番号> --repo=YutoMatsui21/shortcut-expert --head=<最新headの完全SHA>`

2. レビュー未完了なら60秒間隔で再確認する。初回を含め最大5回確認し、それでも未完了なら自動処理を停止してユーザーに報告する。
3. PR Reviewと通常のPRコメント両方を確認する。必要な本文は`--details`で取得する。

**完了判定**
- 最新headへの依頼後のレビュー結果を確認する。👀リアクション、`changed: false`、未解決thread 0だけでは完了と判断しない。
- 取得エラー・結果不明を成功扱いにしない。依頼済みのレビューが未完了ならMergeしない。

### 2.6. CI失敗・レビュー指摘へ対応する

1. CI失敗なら原因を調査し修正する。GitHubレビューを依頼した場合はCIとレビューの両方が完了してから指摘に対応する。
2. 修正内容に応じたローカルテストを実行する。
3. [追加レビュー規則](../../docs/code-review.md#レビュー対象と再レビュー)に基づき、ローカル再レビューの要否を判断する。
   - CI環境・設定のみ：原則不要。
   - テストの期待値・検証条件：仕様との整合性を確認し、必要時に再レビュー。
   - 本番ロジック・重要な契約の変更：原則再レビュー。
4. 再レビューでは、前回のレビュー済みコミット以降の差分とその影響範囲を重点的に見る。小さな修正でも既存の前提が崩れた場合は範囲を広げる。`/review`が自動で差分を限定するとは仮定しない。
5. 修正をpushしたら最新headのCIを再確認する。GitHubレビューを必要としていた場合は、最新headに対するレビューの有効性を確認し、変更でレビュー済みの前提が崩れたときは再依頼する。

**制約**
- 指摘はコードと照合して対応する。P2を見送るときは理由を残す。
- テストを無理に通すために期待値や検証条件を弱めず、Issueの受入条件と照合する。
- 保存・移行に関する変更ではテスト設計Skillの故障境界も確認する。

### 2.7. PRをmergeする

1. 最新headのCI成功、ローカルレビューの実施・必要な再レビューの対応（または省略理由）を確認する。
2. GitHubレビューを依頼した場合は、その完了と重要な指摘への対応を確認する。
3. 未解決thread・競合・branch protection等のMerge条件を確認し、すべて満たしたらmainへmergeする。

**制約**
- CI失敗、必要なレビュー未完了、重大指摘未解決、権限不足ではmergeしない。
- アプリの公開・配布には別途承認が必要。

### 2.8. Issue・ラベルを更新する

1. mainへの取り込みを確認する。
2. 対象Issueを`Closed (completed)`にする。
3. 対象Issueのラベルを更新する。
   - `ready-for-agent`を外す。
   - 不要な`blocked`を外す。
   - `ui-redesign`・`kind:...`などの分類ラベルは残す。
4. 親Issueの進捗を更新する。
5. 後続Issueの着手条件を確認し、すべて満たす場合だけ`blocked`を外して`ready-for-agent`を付ける。

**制約**
- mainへの取り込み前にIssueを完了扱いにしない。
- 保留・対象外Issueを勝手に着手可能に変更しない。

### 2.9. 結果を報告する

- PRとmerge先
- ローカルレビュー・CI・追加GitHubレビュー（実施時）の結果
- 更新したIssue・ラベル
- 未確認事項・残作業

## 3. 例外

- **実装がすでにmainへ反映済み**：重複PRを作らず、取り込み・受入条件を確認してIssueを更新する。
- **調査・Figma等の非実装Issue**：成果物を確認してIssue状態を更新する。不要なPRは作成しない。
- **条件未達・権限不足**：成功や完了を装わず、阻害要因を報告する。
- **アプリの公開・配布**：別途ユーザーの承認を得る。
