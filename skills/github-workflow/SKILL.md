# GitHub操作

GitHub操作はこのSkillに従う。[AGENTS.md](../../AGENTS.md)と対象Issueの受入条件を優先する。コマンドや監視方法の詳細は[開発手順](../../README.md#development-workflow)・[PR監視入口](../../docs/development-tools.md#pr監視)を参照する。

## 1. GitHubの操作方法

1. **GitHub CLI（`gh`）を最優先**で使用する。
2. `gh`が使えない場合に限り、接続済みの`codex.apps`（GitHubアプリ）を使用する。
3. どちらも使えない場合は処理を停止し、ユーザーに報告する。

**判定・制約**
- CLIの利用可否は`gh --version`・`gh auth status`で確認する。
- 情報取得では`--json`・`--jq`を使い、必要な項目だけを取得する。
- 検索結果0件やコマンド失敗だけでCLIが利用不能とは判断しない。原因を確認する。
- 認証・権限は実行環境ごとに確認する。

## 2. 実装Issueの完了フロー

### 2.1. 実装・検証する

1. 対象Issueの受入条件を確認する。
2. 必要な実装・修正を行う。
3. [テスト設計Skill](../test-shortcut-coach/SKILL.md)に従って検証する。

**制約**
- 人工fixtureの成功を実入力精度の証拠にしない。

### 2.2. PRを作成・レビューを依頼する

1. 変更をcommit・pushする。
2. main向けPRがなければ作成する。
3. `@codex review`でレビューを依頼する。

   `gh pr comment <PR番号> --body '@codex review'`

**判定・制約**
- PR本文には対象Issue（例：`Closes #17`）、変更点・テスト結果・未検証事項を記載する。
- Codexの自動レビューは無効のため、PR作成後と以後の各push後に明示的に依頼する。
- 同一headへの重複依頼は避け、投稿成功を確認する。

### 2.3. CIを待つ

1. 最新headの完全SHAを取得する。
2. 以下のコマンドでCIの完了を待つ。

   `gh pr checks <PR番号> --watch --interval 30`

3. `write_stdin`で最大5分間待機する。
   - `chars: ""`
   - `yield_time_ms: 300000`
   - CIが完了したら次へ進む。
   - 5分経過しても実行中なら、同じコマンドを引き続き待つ。

**判定・制約**
- 対象：最新headの必須チェック（`windows-quality`）。
- 出力：実行ログは退避し、Codexには成否など必要最小限の情報だけ返す。
- CI失敗時：結果を記録し、Codexレビューの完了後に修正する。
- コマンドの実行エラーはCI失敗と区別して対応する。
- `write_stdin`は実行環境が対応する最大待機時間を使う。5分はCIの打ち切り時間ではない。

### 2.4. Codexレビューを待つ

1. CI完了後、[PR監視入口](../../docs/development-tools.md#pr監視)のコマンドでレビュー状態を確認する。

   `node scripts/github-workflow.mjs pr-status <PR番号> --repo=YutoMatsui21/shortcut-expert --head=<最新headの完全SHA>`

2. レビュー未完了なら60秒待ち、再確認する。
3. **初回を含めて最大5回**確認する。

**完了判定**
- 最新headに対するレビュー依頼後のCodexレビュー結果を確認する。
- PR Reviewと通常のPRコメントの両方を確認する。
- レビュー依頼コメント、`changed: false`、未解決thread 0だけでは完了と判断しない。
- 結果が不明な場合は未完了として扱う。
- 必要な本文・指摘は`--details`で取得する。

**上限到達時**
- 5回とも未完了なら自動処理を停止する。
- 追加の問い合わせは行わず、ユーザーに状況を報告して手動での再開を依頼する。
- 取得エラーや情報の欠落を成功扱いしない。

### 2.5. 結果に対応する

1. CIとCodexレビューの両結果が揃ったら、失敗・指摘内容を確認する。
2. 必要な修正を実施する。
   - **CI失敗**：原因を調査して修正する。
   - **P0/P1**：必ず対応する。
   - **P2**：影響度・重要度・緊急度を評価し、重要または緊急なバグだけ修正する。
3. 修正内容に応じてテストを実行する。
4. 修正をpushした場合は、最新headに対して再度レビューを依頼し、**2.3から繰り返す**。

**制約**
- CIとレビューの両結果が揃うまで修正しない。
- 指摘はコードと照合してから対応する。
- P2を見送る場合は理由を残す。
- 保存・移行に関わる変更ではテスト設計Skillの故障境界も確認する。

### 2.6. PRをmergeする

1. 最新headのCI成功・Codexレビュー完了を確認する。
2. 必須指摘への対応・未解決thread・競合・branch protectionを確認する。
3. すべての条件を満たしたらmainへmergeする。

**制約**
- CI失敗、レビュー未完了、重大指摘未解決、権限不足の場合はmergeしない。
- 結果を確認できない場合もmergeせず、阻害要因を報告する。

### 2.7. Issue・ラベルを更新する

1. mainへの取り込みを確認する。
2. 対象Issueを`Closed (completed)`にする。
3. 対象Issueのラベルを更新する。
   - `ready-for-agent`を外す。
   - 不要な`blocked`を外す。
   - `ui-redesign`・`kind:...`などの分類ラベルは残す。
4. 親Issueの進捗を更新する。
5. 後続Issueの着手条件を確認し、すべて満たす場合だけ`blocked`を外して`ready-for-agent`を付ける。

**制約**
- mainへの取り込み前にIssueを完了扱いにしない。
- 保留・対象外Issueを勝手に着手可能に変更しない。

### 2.8. 結果を報告する

以下を簡潔に報告する。

- PRとmerge先
- CI・Codexレビューの結果
- 更新したIssue・ラベル
- 未確認事項・残作業

## 3. 例外

- **実装がすでにmainへ反映済み**：重複PRを作らず、取り込み・受入条件を確認してIssueを更新する。
- **調査・Figma等の非実装Issue**：成果物を確認してIssue状態を更新する。不要なPRは作成しない。
- **条件未達・権限不足**：成功や完了を装わず、阻害要因を報告する。
- **アプリの公開・配布**：別途ユーザーの承認を得る。
