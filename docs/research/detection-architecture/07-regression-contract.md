# 07 リファクタリングで維持する検出動作（Step 3）

> **ステータス：既存仕様の整理（変更提案ではない）**。確認元：製品要件・操作別設計・コードとテスト（2026-11-06 の`main` [782dbb79](https://github.com/YutoMatsui21/shortcut-expert/tree/782dbb79b11bf8eea3782ebbf4f299b0f83f76d3)）。製品の受入条件の正本は[製品要件](../../ui-requirements.md)。ここでは検出アーキテクチャのリファクタリングによって**変えてはいけない観測可能な結果**をテストへ結び付ける。

- **目標**：既存のNative候補、Core採用、記録、通知の振る舞いを変えずに内部依存を整理する。
- **対象**：初回対象8操作、複合操作、通信・停止・故障・プライバシー。初回対象外の機能を新たに有効化しない。
- **対象外**：検出の新規機能・採用条件の緩和、JSON Lines protocolの変更、過去の実測を今のbuildの合格へ読み替えること。
- **検証の注意**：ここに「守る」と書いた動作が**全て今の自動テストで保証されているという意味ではない**。実際の対応は[08 テスト対応表](08-test-coverage.md)へ記す。

## 1. Native → Coreの共通条件

| ID | 変えてはいけない結果 | 根拠・着目点 |
| --- | --- | --- |
| **R01** | 同じ入力とその結果を、同一の対象ウィンドウ・process・入力由来・時間内・非注入/非競合として関連付ける。不明な対象や不確かな結果を勝手に採用しない | `Observer`のstate読取と`CandidateTracker`、各専用Policy |

| **R03** | 注入・修飾キー競合、違う窓、foreground不一致、期限切れ、対象破棄、停止・世代変更等の既存取消条件を維持する。操作専有の優先関係を壊さない | Native `OnMouse/OnKey/OnEvent`の分岐、各Policyの`Cancel/Reset` |

## 3. 複合操作と境界

| ID | 対象 | 正常な結果・守る制約 |
| --- | --- | --- |
| **R12** | **W01＋W03/W04** 非アクティブcaptionクリック | **1物理クリック→同一transactionの1Candidate**。前景切替を確認できればW01、独立に最大化/最小化終状態を確認できればW03/W04。両方成立すれば2件を原子的に保存。部分的な証拠不成立では、その部分を推測しない。全条件不成立なら0件 |
| **R13** | **W02＋W03/W07** 別画面複合ドラッグ | 同じ物理ドラッグで別画面移動＋最大化/四隅が成立した場合、**1Candidate→2つの異なるObservation**。派生W04・中間W06を計上しない。**不正な複合Evidenceは片方だけ採用せず全体棄却**。別画面へ半分配置（W02＋W06）は今回の確定対象外 |
| **R14** | **1gestureの保存・通知** | 2件の場合も**同じSQLite mutation/transaction**に保存し、途中失敗なら両方rollback。記録成功後に適格な行だけ1つの通知へまとめる。未確証キーは通知しない。再送・ACK喪失・保存失敗・stop・pauseで古い通知を復活させない |

根拠：[compound-caption-click](../../operations/compound-caption-click.md)、[compound-drag](../../operations/compound-drag.md)、[durable-storage](../../storage/durable-storage.md)。

**現行の上限**：`classifyGesture`は現状0～2件、`DurableCoach.prepare(counts[0], undefined, counts[1])`も2件の原子保存を扱う。将来3件以上を扱う拡張は**別機能**であり、このリファクタで無断変更しない。

## 5. 検証結果の読み方

- **自動unit/Native policy**：条件分岐や人工イベント列、候補の形式、回帰動作を検証するが、実Windowsからコールバックが期待どおり届くとは証明しない。
- **helper process/IPC**：実C#プロセスの起動・応答・JSONL・TS受信を検証するが、自然入力を証明しない。
- **実SQLite統合**：保存・二重計上防止・通知adapter呼出しは確認できるが、Windows通知がユーザーに表示されたかとは別。
- **自然入力受入**：最終buildの物理マウス・キー操作、代表アプリやモニター構成などを人が確認。別のrevisionの過去検証を現在のPASSにしない。

**この文書作成時にテストは実行していない**。静的にテストの内容と設計・製品要件を照合したもの。どのテストが何を守るかは[08 テスト対応表](08-test-coverage.md)。

## 6. Step 4で必ず使用する受入条件

1. 各コード変更PRについて、影響する`R01～R19`を明記し、対応する既存/追加テストを実行する。
2. CandidateのJSONLと`Observation[]`の結果・保存件数・通知要求を、**構造変更前と同じ入力で比較**する。OS時刻等の揺らぎを除き、実際の判断に影響するフィールドを検証する。
3. イベント配信・候補の確定・競合の順序を変更するPRでは、**Observerから複数Handlerへ到達する一連の入力列**を対象にした回帰テストを先に補強する。
4. 実装・C#・TS・CIの変更はWindowsフルCI対象とし、必要なら本人の明示同意に基づく自然入力受入を別途行う。
5. 新たな採用条件・検出対象・protocolを変える場合は「単なるリファクタリング」として実施しない。
