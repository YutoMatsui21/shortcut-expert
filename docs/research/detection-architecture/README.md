# 検出アーキテクチャ

**目的**：操作を追加するときに既存コードの変更を最小限にするため、現行実装と目標設計を分けて管理する。

| 知りたいこと               | 読む文書                             | 状態                         |
| -------------------------- | ------------------------------------ | ---------------------------- |
| **今どう動いているか**     | [現在の構成](current.md)             | 現行コードの説明             |
| **どの構造を目指すか**     | [目標アーキテクチャ](target.md)      | 採用する設計（未実装）       |
| **どう変更するか**         | [リファクタリング計画](migration.md) | 実装順序・完了条件（未着手） |
| **何を壊してはいけないか** | [回帰条件とテスト](verification.md)  | 既存動作を守るための検証仕様 |

## 設計を見直すための調査

- [各操作の現行検出方法](independence/current-detection-methods.md) — 8操作それぞれの入力・開始状態・終了状態・除外条件と、見直し候補を整理。
- [理想の検出条件とAPI実現可能性](independence/ideal-feasibility-and-proposal.md) — マウス/キー別の**理想・技術的制約・現実案**。**比較検討中で未採用**。
- [各操作の独立検出可能性](independence/README.md) — 8操作の依存・独立化の見込み・実証すべき条件。**静的調査であり、新しいAggregator方式の採用決定ではない**。

## 最初に押さえること

- **現在**：C#の`Observer`がイベント取得だけでなく、`CandidateTracker`や専用Observerの呼出し・競合・取消も担う。
- **目標**：ObserverはOS観測に集中し、`DetectionRouter`と`ArbitrationPolicy`が配信・競合を制御。各HandlerがOS証拠を生成し、TypeScriptが操作IDと案内キーを判定する。
- **移行中も変えない**：Candidate JSONL protocol v2、初回対象8操作、入力の確証条件、複合操作、SQLite記録、通知の振る舞い。

**Codexの参照順**：`current.md` → `target.md` → `migration.md` → `verification.md`。変更対象が明確な場合は該当文書だけでよい。

**正本の優先順位**：製品の振る舞いは[製品要件](../../ui-requirements.md)、操作別の成立条件は[操作別設計](../../operations/README.md)、全体の責務は[全体設計](../../design.md)。このフォルダは**検出の現状把握とリファクタリング仕様**に限定する。実装済みかどうかは最新コード・テスト・Issue/PRで確認する。文書を更新するときは、歴史的な追記を増やさず該当ページを直接修正する。
