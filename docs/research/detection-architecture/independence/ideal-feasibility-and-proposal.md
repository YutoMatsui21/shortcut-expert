## 1. 最初に決める共通原則

**成立条件 = 適格な入力 + 開始状態 + 確証された終了状態・結果 + 入力と結果の対応関係**。

| 要素     | 意味                                           | 例・注意                                                                                                   |
| -------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 入力     | 誰が、どこで、何をしたか                       | 物理的なクリック/2回クリック/ドラッグ、Win+↑等。合成入力・追加修飾・誤入力は区別                           |
| 開始状態 | **対象の入力直前**の状態                       | 前面ウィンドウ、同一HWND/process、通常/最大化/最小化、**半分の左右や四隅の位置を含む配置形状**、monitor    |
| 終了状態 | **OS側で結果が確定した時点**の状態             | 終了時のforeground、対象のshow state、配置shape、monitor、ウィンドウの消滅／タスクバー項目の照合           |
| 対応関係 | 観測された入力による同じ対象の変化と言える根拠 | 同一root/一時的なHWND・process・thread、物理入力の押下・解放、WinEventの順序、対象と期限、画面構成の安定性 |

- **途中のウィンドウサイズ変化・中間halfなどを別操作として計上しない**。ただし「ドラッグ中だった」「Winを保持していた」「Alt+Tabが完了した」等、**入力の継続/終了を示す最小限の事実**は必要。**入力終了 ≠ OS結果確定**なので、解放後も必要な結果の照会を行う。
- **同じ形状かどうか**は単に `normal/maximized` だけで比較しない。W06の左half→右half、W07の左上→右上も**配置が変化**している。一方「最大化A→最大化B」は**状態の最大化自体は変わらない**のでW03でなくW02。
- 他操作の判定成功を各検出器の成立条件にしない。ただしW12由来のforegroundをW01に数えない、ドラッグ派生の復元W04・途中half W06を数えない等、**物理入力の由来と一連の操作の区切り**は共有する。
- **情報不明なら推測計上しない**を基本にする。一方「操作としては確証、代替キーの同等性だけ不明」は**記録のみ／キー通知なし**を許す。単純に全ての候補を無条件で統合しない。
- 同一ジェスチャから複数の操作が確証された場合、**一つのジェスチャIDと候補にまとめてから送信**する現行v2/transaction/原子SQLite保存との整合が必要。検出器の独立性と、出力経路の互換性は別問題。
- 生HWND・process・座標列・アプリ名などの一時的な内部照合情報は**永続化・IPCに出さない**現行のプライバシー境界を維持する。

## 2. 技術的な実現可能性の評価尺度

| 判定                     | 意味                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------- |
| **取得可能**             | Win32/フック/WinEventなどで、必要な**入力や状態の素材**を取得できる（その操作が成立した保証ではない） |
| **照合可能（条件付き）** | 入力と結果の照合により推定できるが、アプリ/イベント順序/表示構成次第で欠測・誤判定のリスクがある      |
| **不確実**               | 独自UI・UIA・未公開情報・曖昧な因果等に依存し、実機試験なしに一般対応を主張できない                   |

**重要なAPI上の制約**

1. `WH_MOUSE_LL`は**左down/upと移動**などを通知するが、「対象アプリが意味的に何のボタンを押されたか」を必ず返すわけではない。**ダブルクリック専用イベントが低レベルフックから来る前提にしない**。2回のdown/up・同一対象・距離・`GetDoubleClickTime`による相関で判定する。
2. `WM_NCHITTEST`の`HTCAPTION`や`HTMAXBUTTON`、`TITLEBARINFOEX`は使えるが、**独自タイトルバーではアプリ側のhit test/アクセシビリティ実装次第**。`HTCLIENT`でも視覚的にはタイトルバーかもしれない。**場所がタイトルバーだったことを外部から一般に証明するAPIはない**。
3. `WH_KEYBOARD_LL`でキー種別・down/up・注入フラグを取得できるが、コールバック内の`GetAsyncKeyState`は**そのキーの最新状態が反映される前**の場合がある。保持キーは内部の入力系列でも照合する必要がある。
4. `GetWindowPlacement`等でshow state、`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`とmonitorのwork areaで幾何を確認できる。ただし**「Windows標準のSnap操作だった」という因果ラベルではない**。DPI/配置/端付近の判定・`IsWindowArranged`の実環境での利用可否を検証する。
5. `EVENT_SYSTEM_FOREGROUND`、`MOVESIZESTART/END`、`MINIMIZESTART/END`、`EVENT_OBJECT_DESTROY`等で結果の機会を観測する。しかし全状態変更に原因入力IDが付与されるわけではない。**アプリが独自に状態変更する場合や、イベントの遅延・欠落**は実機確認が必要。
6. `MonitorFromWindow`はウィンドウが複数monitorにまたがる場合に**交差面積が最大のmonitor**を返す。monitor識別は結果の読み取り方法に依存する。UIAはタスクバー項目の照会に役立つが、そのツリー/要素の存在は将来のすべての環境で保証されない。
7. `IsWindow`確認と結果処理の間にも対象ウィンドウは破棄・HWND再利用され得るため、**一時的な対象同一性とgeneration/期限の確認**は省略しない。

## 3. 8操作の理想条件 → 実現性 → 現実案

以下の「現実案」は**採用する場合の推奨条件**であって、実装・実機精度が確認済みという意味ではない。各行の対応関係に加え、§1の共通条件を必須とする。

### W01：ウィンドウ切替

| 経路   | 理想（入力・開始→終了）                                  | 技術的実現性                                                                                                                       | 現実案                                                                                                                                                                                      |
| ------ | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| マウス | 非アクティブの適格ウィンドウBを直接クリック。**前面A→B** | **照合可能**：物理down/up＋root対象＋foregroundイベント、終了時照会を相関。独自captionの適格性と最小化ボタン後の一時的前面化に注意 | 対象Bへの適格な直接入力、物理解放、**クリック後のB前面化の確証**を要求。Bを最小化した結果、最終foregroundがCになっても、一時的なB前面化の確証があればW01を認める。W12のタスクバー入力は除外 |
| キー   | Alt+Tabを1回以上使い、Altを離して**前面A→B**             | **照合可能**：Alt/Tab入力とforeground＋settle照会。Shell中間ウィンドウは一時状態なので除外                                         | 同一Alt保持系列を1操作とし、Alt解放後の最終適格ウィンドウBを確証。中間ウィンドウ・元のAへ復帰・Escは不成立                                                                                  |

**他操作との関係**：非アクティブウィンドウの最大化/最小化ボタンクリックは**W01＋W03/W04**になり得る。一方、タスクバーアイコン/Win+数字による前面移動やW11による閉鎖後の自然なforeground変更はW01にしない。専用`InactiveCaptionHandler`を削除できるかは**未証明**。

### W02：別画面移動

| 経路   | 理想（入力・開始→終了）                                                                                          | 技術的実現性                                                                                                         | 現実案                                                                                                                                                         |
| ------ | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| マウス | **同じウィンドウを物理ドラッグ**。monitor A→B（A≠B）。開始/終了の最大化・整列状態は**W02成立の必須条件にしない** | **照合可能**：down/up＋`MOVESIZESTART/END`＋始終monitorを観測。独自ドラッグ、monitor判定・DPI/レイアウト変更で不確実 | 同一対象のドラッグ確証・安定したmonitor構成・物理解放・Bへの移動を要求。**最大化A→最大化BでもW02を採用する案**。途中の一時復元はW04として採用しない            |
| キー   | Win+Shift+←/→の確証済み系列でA→B                                                                                 | **取得＋照合可能**：キー系列、対象、monitor比較                                                                      | 物理入力と入力対象を保持し、方向キー解放後に同じウィンドウのmonitor差を確認。元のmonitorへ戻ったら0件。方向/キー同等性が不明でも**移動の確証があれば記録のみ** |

**他操作との関係**：同じドラッグで**非最大化→最大化**まで成立した場合はW02＋W03、別の四隅形状になればW02＋W07の候補。**最大化A→最大化BではW02のみ**。**W02＋W06（別画面に移しhalfへ配置）は現行仕様で未対応**なので、独立検出の結果として自動採用せず、**仕様拡張の判断保留**にする。

### W03：最大化

| 経路   | 理想（入力・開始→終了）                                                                                                      | 技術的実現性                                                                                                                       | 現実案                                                                                                                                                                                                                                   |
| ------ | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| マウス | 最大化ボタン、タイトルバー相当領域のダブルクリック、上端ドラッグ。**表示中の非最大化→最大化**（通常サイズや半分/四隅から可） | **ボタン/標準captionは取得可能、独自captionは不確実**。上端解放＋最終show stateは照合可能。ダブルクリック自体はdown/up系列から推定 | ①明確なボタン・captionを優先。②不明領域の**同じウィンドウ・近い位置での2クリック**と最大化確証を組み合わせる補完案は**実機の誤検出評価後に採否判断**。③ドラッグは上端解放・MOVESIZEEND・最終最大化を確認。**開始`normal`限定は緩和候補** |
| キー   | Win+↑を含む適格な入力系列で**非最大化→最大化**                                                                               | **取得＋照合可能**：キー入力とshow state。整列から1回で最大化になるとは限らず、複数↑の扱い要注意                                   | 同じ対象のWin+↑入力系列と最終最大化を照合。キーrepeatを別計上せず、必要な連続押下を**1操作としてまとめる条件**は別途自然入力検証。対象/結果不一致は棄却                                                                                  |

**補完の線引きが重要**：**「どこでもダブルクリック＋最大化なら必ず標準のタイトルバー操作だった」ことは証明できない**。アプリ内コンテンツへのダブルクリックでアプリ独自に最大化した可能性がある。現行の`mouse-state-fallback`は**ダブルクリックに限定せず、短時間のクリックと状態変化でも採用する**ので、新しい2クリック案へ変える場合は**誤検出だけでなく既存の検出率低下**も比較する。

### W04：最大化解除・最小化（1つのW ID）

| 経路   | 理想（入力・開始→終了）                                                                         | 技術的実現性                                                                                        | 現実案                                                                                                                                                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| マウス | 復元ボタン/適格なダブルクリックで**最大化→通常サイズ**、または最小化ボタンで**非最小化→最小化** | **照合可能・独自captionは不確実**：ボタン/2クリック候補、show state。最小化後のforeground変更は自然 | まず明示的ボタン/標準captionを採用。未知領域は対象一致・解放・状態遷移で補完候補とするが、**単クリック/2クリックの許容範囲を実機評価**。最小化で最終foregroundが対象以外になっても許す                                            |
| キー   | Win+↓の確証済み系列。**最大化→通常**、または**非最小化→最小化**                                 | **取得＋照合可能**：入力列、開始show/最終show。ただし2回押下の連続解釈と確定タイミングは仕様判断    | 同じウィンドウへの物理Win+↓の確証と結果を要求。**最大化解除→最小化を継続とする場合はW04を1件**、キーrepeatは別押下と数えない。現行は最初の確定時に1件計上し、次の同一系列を抑制する。計上タイミングを変えるなら明示的に合意を取る |

**抑制**：ドラッグ中の最大化解除や途中の配置変更は**W04ではない**。「開始と終了の差だけ」で判定せず、**W04に対応するマウス/キー入力があったこと**を必須とする。キー同等性が曖昧な最小化は、既存同様、記録と通知可否を分ける。

### W06：左右半分への配置

| 経路   | 理想（入力・開始→終了）                                                                 | 技術的実現性                                                                                   | 現実案                                                                                                                                                  |
| ------ | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| マウス | ウィンドウを左右端へドラッグし、**終了が左halfか右half、かつ開始時と配置shapeが異なる** | **条件付き**：MOVESIZEと物理解放、DWM枠/作業域を照合。Snap UIやカスタムcaption、座標誤差に依存 | 解放点が対応端付近で、同じウィンドウ・最終half形状を確証。**開始`arranged=false`限定は撤廃候補**。右half→左halfもW06。元と同じhalfへの再配置は不成立    |
| キー   | Win保持の方向キー列で、最終配置が**開始と異なる左右half**                               | **取得＋照合可能**：キー保持/解放＋DWM配置幾何                                                 | Winを押した一連の入力が終わってから最終形状を確定。途中のhalfは採用せず、**同じ列でquarterになればW07のみ**。複合系列で代替キーを案内できるかは個別照合 |

**区別**：右half→左halfは状態名が同じでも配置変更なのでW06。一方、右half→右half（別monitorに移っただけ）ならW02のみ。ドラッグなしの通常リサイズやSnap Layout内の選択は、入力因果を確証できない限りW06としない。

### W07：四隅への配置

| 経路   | 理想（入力・開始→終了）                                  | 技術的実現性                                                                                              | 現実案                                                                                                                              |
| ------ | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |

| キー   | Win保持の方向キー列で、最終配置が**開始と異なるquarter** | **取得＋照合可能**：保持キー列・対象・最終shape                                                           | Win解放後の最終quarterだけを採用。開始half→quarterはW07のみ。quarter A→quarter Bも成立。キーの最終方向とshapeが不一致なら棄却       |

**複合**：同一ドラッグで別monitorへ移りquarterに配置されたら、W02＋W07（ただし各々の証拠とジェスチャ全体の一貫性が必要）。中間halfをW06にしない。

### W11：ウィンドウを閉じる

| 経路   | 理想（入力・開始→終了）                                           | 技術的実現性                                                                                             | 現実案                                                                                                                                                      |
| ------ | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| マウス | 適格ウィンドウの閉じるボタンを押し、**対象ウィンドウが存在→消滅** | **条件付き**：標準ボタンは矩形/hit test、カスタムUIは不確実。DESTROYイベントとウィンドウ消滅の確認は可能 | 閉じるボタンだと**明示的に裏付けられる入力だけ**採用。同じ対象の解放、DESTROY＋消滅を照合。未知の場所での単クリック→ウィンドウ消滅だけでW11と**推定しない** |
| キー   | Alt+F4を対象ウィンドウに入力し、**対象ウィンドウが存在→消滅**     | **取得＋照合可能**：キー系列とDESTROY＋消滅。ただし確認ダイアログやhide、HWND再利用に注意                | 適格ウィンドウでの物理Alt+F4と同じHWND/process/threadを照合し、DESTROY＋実消滅まで期限内に確認。単なるhide/確認ダイアログでは不成立                         |

**補足**：最終foregroundが別ウィンドウになっただけではW01/W11を新規に計上しない。ウィンドウIDの取り扱いでは`IsWindow`単独の時点チェックを過信しない。

### W12：タスクバーからアプリを開く・切り替える（現行仕様を維持）

| 経路   | 理想（入力・開始→終了）                                          | 技術的実現性                                                                            | 現実案                                                                                                                                      |
| ------ | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| マウス | タスクバー上の**実在するアプリ項目**をクリックし、同じ項目で解放 | **条件付き**：UIAでアイコン列とslotが取れる環境は可能。UIA要素が不明/変動すると確証不可 | 対象の主タスクバーitem/slot/同一性を入力前後のUIA照会で確証。**アプリの新規起動/既起動を区別しない**。slot不明なら棄却、W01へfallbackしない |
| キー   | 実在するslotへのWin+1〜9/0                                       | **取得＋条件付き照合**：入力は確証可能。ただし**実在slotとの対応にはUIA情報**が必要     | 物理Win+数字の初回keydown＋有効slotをUIA照合。UIAが不明なら無計上。キーrepeat・追加修飾は不成立                                             |

**仕様維持**：W12は**アプリの新規起動のみを意味しない**。WindowsのWin+数字は起動済みアプリへの切替にも使えるが、タスクバー操作としてW12に計上する。タスクバー以外への直接クリックとAlt+TabをW01とする既存の区別を変えない。

## 4. 現行との差分と採用判断

| 論点                                  | 現行                                                                    | 今回の現実案                                                                               | 判断                               |
| ------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------- |
| **W02 マウスの終了show state**        | 単独経路はnormal/非整列。複合は終端形状で別処理                         | 画面A→Bの事実が確証できれば、**開始/終了の最大化・配置はW02の除外理由にしない**            | **推奨、未実証**                   |

## 6. 暫定結論

**理想原則は共通化できそうで、W02/W03/W06/W07の開始・終了制限は見直す価値が高い**。ただし操作の一部がWindowsの非公開/アプリ独自UIに依存するため、**入力・開始/終了差分だけから正しい操作を100%識別できるとは言えない**。

採用判断は **(A)明確な入力＋状態で成立、(B)不明領域は限定的fallback候補、(C)入力/因果が不明なら記録しない** を基本に、実機検証後に決める。**この提案をもって既存`target.md`／`migration.md`や製品仕様を変更しない**。
