# 追加コードレビュー規則

Codexの既定のバグ判定基準を置き換えず、変更が仕様を満たしているかを判断する調査手順を補う。
本書はレビュー用の規則であり、要件・設計・テストの正本ではない。重要な指摘は今回の変更に起因し、再現条件と根拠があるものに限定する。

## 1. 仕様適合性

1. 対象Issueの目的・受入条件、関係する[要件](ui-requirements.md)・[技術判断](archive/research-overview.md#operations)・[設計](design.md)の必要な節を確認する。
2. 各受入条件について対応する実装を特定し、未達・挙動の不一致・意図しない仕様変更を調べる。
3. 曖昧な仕様を勝手に補完せず、根拠がない指摘と確認できない事項を区別する。

## 2. 変更の影響範囲

1. 変更した関数・型・状態・インターフェースの利用箇所を絞って調べる。
2. 関連する呼出し経路・状態遷移・保存形式などの契約を追い、今回の変更で起こる回帰を確認する。
3. 無関係なファイル全体へ調査を広げない。差分外に原因があると言う場合は、影響を受ける具体的なコードを示す。

## 3. 境界条件・テスト

1. 変更の性質に応じて、境界値・異常系・入力順序・競合・停止・復旧・保存失敗を確認する。
2. 既存テストが重要な振る舞いを検証しているか確認し、必要なら変更に対応する試験を実行する。
3. テストの削除・期待値変更・skipは、仕様に照らして検証を弱めていないか調べる。
4. テスト設計の正本は[設計書のテスト章](design.md#test-design)と[テスト設計Skill](../.agents/skills/test-shortcut-coach/SKILL.md)。人工fixtureの成功を自然入力の認識精度の証拠にしない。
5. テスト不足だけを機械的にバグ扱いせず、具体的な不具合や重要な未検証経路を根拠とともに示す。

## 4. 変更固有の重点

1. 対象Issue・差分から今回の重要な失敗モードを選ぶ。明示的な重点指示があれば優先する。
2. その失敗モードの成立条件・関連コード・既存テストを確認する。
3. 重点外の重大な問題も見逃さず、報告する。

## レビュー対象と再レビュー

- **PR前**：変更全体を対象とする。対話時はローカル`/review`でベースブランチとの差分、または未コミットの変更を選ぶ。実装Agentが自動実行するときは`codex review --base main`（または`codex review --uncommitted`）を使い、未コミット分も含め意図したファイルが対象か確認する。
- **レビュー指摘の修正後**：変更による新たな挙動や重要な契約への影響があれば再レビューする。検証済みという判断の根拠を記録する。
- **CI失敗後**：まず失敗原因と修正内容を確認する。CI環境・設定のみの修正は原則再レビュー不要。テスト期待値の変更は受入条件を照合し、本番ロジック・重要な契約を変えた場合は原則再レビューする。
- **再レビュー範囲**：前回レビュー済みのコミットを記録し、以後の変更差分とその利用先・影響範囲を重点的に確認する。単に修正行だけに限定しない。複数コミットの正確な差分が`/review`で指定できない場合は、差分を別途確認してカスタム指示に明示するか、安全側に変更全体を再レビューする。`/review`が自動的に前回以降の差分へ限定されるとはみなさない。

## 出力と実行上の制約

- 指摘には、発生条件・影響・関連箇所を簡潔に示し、確実でない推測を確定事項として報告しない。
- デフォルトの優先度・重複除去・出力形式を維持する。PRの既存バグや軽微なスタイル変更を新規の欠陥として扱わない。
- `AGENTS.md`からの参照だけで、本書が`/review`や`codex review`の専用レビュアーに自動適用される保証はない。レビュー開始時に参照の有無を確認し、必要ならカスタムレビュー指示へ重要な観点を直接記載する。`codex review`の対象指定フラグとカスタムPROMPTは同時指定できないため、後者では対象差分も文章で指定して確認する。
- `/review`は調査のみ。修正・テスト・commit・pushはレビュー結果を受け取った実装Agentが行う。
